# Phase 6 — reviewed RAG golden evaluation set

Status: **COMPLETE — a versioned, corpus-bound golden set is committed;
retrieval and generation configuration were not changed.**

Completed: 2026-08-25  
Scope: evaluation-set design and evidence review only. Phase 7 measurement and
any retrieval/model tuning are intentionally not started.

## Artifact

The versioned set is:

```text
evaluation/rag_gold_v1.json
```

It contains 11 reviewed examples covering every required question class:

- direct fact;
- multi-paragraph answer;
- multi-page answer;
- policy interpretation;
- cross-document question;
- ambiguous question;
- no-answer question;
- role-restricted question;
- similar-document confusion case; and
- table-related question.

The set is deliberately small enough for a human to inspect. It is not a
synthetic list of hundreds of prompts and it is not a quality score.

## How the set was created

1. Inspected the live indexed corpus through `pms_doc.document_record` and
   `pms_vector.document_chunk`.
2. Selected policy, by-law, tender-condition, and clarification documents. No
   tenant-identifying records or private applicant/property rows were copied
   into the evaluation artifact.
3. Read the source-backed page/chunk content for each selected case. Expected
   facts are short, manually written summaries anchored to the source page;
   they were not generated by the same LLM that will later be evaluated.
4. Recorded the exact source filename, SHA-256, and page list for every
   positive case. Negative cases intentionally use an empty expected-document
   list where the corpus has no answer.
5. Added a live-reference test that fails if a source document hash, indexed
   state, or expected page/chunk reference changes.

The source document hashes make the set a snapshot contract rather than a
loose filename-based prompt list. If a source PDF is replaced, the set must be
reviewed and versioned again instead of silently accepting new evidence.

## Schema contract

Each example contains the required fields:

| Field | Meaning |
|---|---|
| `question` | The user question to submit to the RAG system |
| `expected_documents` | Source filename, SHA-256, and expected page list |
| `expected_pages` | Union of all pages that should support the answer |
| `expected_supporting_fact` | Human-reviewed fact or abstention expectation |
| `allowed_role` | Role under which the case is evaluated (`authority` or `tenant`) |
| `answer_should_exist` | Whether a grounded answer is expected |
| `review_status` | Current human-review state; all Phase 6 cases are `reviewed` |

The set also records the corpus snapshot (48 indexed documents, 3,399 chunks,
3,399 embeddings, `bge-m3`, 1024 dimensions) and explicitly states that
retrieval configuration was not changed for its creation.

## Important case decisions

### Later-versus-base policy documents

The cross-document and similar-document cases deliberately pair the PGLM
compilation with the 2018/2019 clarification circulars. The expected answer
must identify later clarification text and must not merge similarly worded
policy passages into one undated rule.

### Ambiguous and no-answer cases

The ambiguous lease-rent case has supporting policy pages but is marked
`answer_should_exist: false` because property, area, purpose, term, and rate
context are missing. The 2030 throughput case has no supporting source pages
and must abstain. These cases distinguish “retrieved something related” from
“the corpus supports a reliable answer.”

### Role-restricted case

The private tenant-account question is a negative authorization boundary. The
current indexed chunks have empty ACL arrays, so this case does not claim that
the policy PDFs carry a role-specific ACL. It verifies that the application
does not fabricate private account data or bypass portal permissions merely
because a role is supplied.

### Table case

The By-law No. 9 Appendix A rate was checked against the rendered source page,
not inferred solely from its noisy extracted table text. This preserves a
review path for table extraction without changing the ingestion or retrieval
pipeline in Phase 6.

## Validation

The following checks pass against the current local database:

- all ten required question types are present;
- all examples are marked `reviewed` and have a supporting fact/abstention
  statement;
- every positive source filename exists and has the recorded SHA-256;
- every positive source is currently `indexed`;
- every expected page has an indexed chunk;
- The full backend suite remains green (43 tests, including the two Phase 6
  gold-set reference tests).

The golden set is evidence for the existing architecture. It does not assert
that retrieval is already accurate, and it must not be used to justify model,
reranker, RRF, retrieval-limit, chunking, or LLM changes in this phase.

Phase 6 stops here. Phase 7 may run the existing retrieval against this set
and calculate metrics, but that work requires a separate explicit phase.
