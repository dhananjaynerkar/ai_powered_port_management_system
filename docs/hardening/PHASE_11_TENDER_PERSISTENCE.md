# Phase 11 — Tender workflow persistence and storage decision

**Date:** 2026-08-25  
**Status:** **PARTIAL / BLOCKED FOR MULTI-USER ACCEPTANCE**  
**Scope:** The JSON-backed tender workflow was exercised only through a disposable temporary store. The committed workflow file and PMS source tables were not modified. No storage migration was performed.

## Gate decision

The current JSON store is acceptable only for an explicitly approved **single-user, single-process local** deployment. It is not sufficient for controlled multi-user or production multi-process use.

The code uses an instance-local `threading.RLock`, a fixed sibling `tender_workflows.tmp`, and `Path.replace`. That provides a useful local atomic-write shape, but it does not coordinate separate service instances/processes. The safe temporary concurrency probe produced one successful writer and one `PermissionError` caused by both writers using the same temporary filename; only one record persisted. This is an integrity failure for a multi-process workflow store.

The repository does not explicitly record the approved deployment target. The README calls the project local-first and the settings default to `deployment_environment=local`, while the application also exposes Authority/Tenant roles and internal/production security gates. Until the owner confirms the deployment mode, no migration should be applied.

## Persistence risks found

1. **Process-local lock only.** `threading.RLock` protects one service instance, not another process or worker.
2. **Shared temporary filename.** Concurrent writers collide on `<store>.tmp`; one writer can fail or a future implementation could overwrite another writer's staged content.
3. **No optimistic version.** Records have timestamps/events but no monotonic `row_version` or compare-and-swap precondition. A stale writer cannot be detected at the storage boundary.
4. **Corruption is hidden.** `_load_records` converts invalid JSON, I/O errors, and non-list JSON into `[]`. A damaged store can therefore look like a brand-new empty system.
5. **Orphan cleanup is absent.** A failed replacement leaves the temporary file in place.
6. **No durable commit protocol.** The writer does not fsync the temporary file or directory before replacement, and there is no recovery journal or checksum.
7. **No storage-path validation.** A custom/mounted storage path with a missing parent fails at write time rather than being validated at startup.
8. **No multi-user audit boundary in the JSON record.** API audit events are written to the application database, but the JSON workflow event does not carry an authenticated actor/principal field. The record itself cannot independently prove who performed each action.

These are storage findings, not a request to change the current workflow behavior in this phase.

## Deployment decision matrix

| Deployment target | JSON suitability | Decision |
|---|---|---|
| Single-user / single-process local | Works for demos and local development when the directory is writable and backed up. Restart persistence was verified in the disposable probe. | Acceptable only with an explicit local-only decision and clear corruption/backup warnings. |
| Controlled multi-user | Not proven. Separate service instances are not serialized and can collide or overwrite. | Do not accept without a transactional shared store. |
| Production multi-process | Not acceptable. Worker/process concurrency, durability, migration, backup, and actor identity are not guaranteed. | PostgreSQL-backed workflow state is required before production approval. |

## PostgreSQL migration design (design only; not applied)

The existing JSON shape can be migrated behind the current `TenderWorkflowService` interface so API routes and UI payloads remain stable.

### Target tables

Use the configured application schema (normally `rag`), not the PMS `public` source schema:

```text
rag.tender_workflow
  workflow_id uuid primary key
  status text not null
  plot_id text not null
  plot_label text not null
  source_snapshot jsonb not null
  plot_mapping jsonb not null
  fields jsonb not null
  calculation jsonb not null
  checklist_key text not null
  checklist_label text not null
  checklist_source_file text not null
  row_version bigint not null default 1
  created_by_principal text null
  created_at timestamptz not null
  updated_at timestamptz not null

rag.tender_workflow_checklist_item
  workflow_id uuid references rag.tender_workflow on delete cascade
  item_key text
  item_number text
  label text
  source_answer text
  source_remarks text
  answer text
  primary key (workflow_id, item_key)

rag.tender_workflow_event
  event_id uuid primary key
  workflow_id uuid references rag.tender_workflow on delete cascade
  actor_principal text null
  action text not null
  from_status text null
  to_status text not null
  comment text not null default ''
  pending_requirements jsonb not null default '{}'
  created_at timestamptz not null
```

Generated PDFs should remain on-demand initially. If retention is later required, add a document metadata table with kind, content hash, generator version, and an approved object-storage/`bytea` policy; do not silently store mutable binaries in the workflow row.

### Relationships and source boundary

- `tender_workflow_checklist_item` and `tender_workflow_event` cascade from the workflow.
- `plot_id` remains an external/source identifier because the workflow uses copied/exported tender source data and the PMS `public.*` schema is read-only for this portal.
- No foreign key or write is added to PMS source tables.
- Existing `audit_event` rows should record API actor, workflow ID, action, and resulting status in the same transaction as the workflow mutation.

### Transaction and concurrency strategy

1. Begin a PostgreSQL transaction.
2. Load the workflow row with `SELECT ... FOR UPDATE`.
3. Validate the action, current status, required fields/comments, and an optional client-supplied `row_version`.
4. Update the workflow and increment `row_version`.
5. Insert checklist changes and one immutable event row.
6. Insert the application audit event.
7. Commit; return the same response shape currently returned by the JSON service.

For stale clients, require `expected_row_version`; return a conflict instead of silently overwriting. Retry only safe reads, not workflow transitions. Keep source reads outside mutation writes where possible, or include them in the same transaction when a source snapshot must be reproducible.

### Migration steps

1. Obtain approval for the deployment target, schema name, retention, and actor/principal mapping.
2. Add an idempotent application-schema migration and storage adapter behind a feature flag; do not alter `public.*`.
3. Validate every JSON record against the configured statuses/actions and quarantine invalid records rather than importing them silently.
4. Import records, checklist items, and events with stable IDs and record a source-file hash/import batch ID.
5. Reconcile counts, status counts, event counts, source snapshots, and generated-document hashes in a disposable database schema.
6. Run dual-read comparison (JSON vs PostgreSQL) without dual-write until responses match.
7. Cut over reads, then writes, with an explicit rollback switch.
8. Keep the JSON file read-only as a rollback/archive artifact until the retention decision is complete.

### Rollback

- Disable the PostgreSQL feature flag and restore the last verified JSON archive only if no post-cutover writes must be preserved.
- If post-cutover writes exist, export them first and reconcile them before rollback; never overwrite the archive blindly.
- Preserve migration logs, record hashes, and the import batch identifier.

### API compatibility

Keep the existing route paths, status keys, action keys, error semantics, PDF kinds, and response payloads. Replace only the service storage adapter. Add an optional `row_version`/conflict field in a backward-compatible response extension and accept an optional expected version in action requests once the API contract is approved.

### Required migration tests

- import/restart/count/status/event reconciliation;
- two concurrent transitions with one deterministic conflict;
- stale version rejection;
- required return-comment enforcement;
- invalid action rejection;
- transaction rollback on checklist/event/audit failure;
- source `public.*` write guard;
- PDF byte/hash reproducibility;
- backup/restore of workflow rows and event history;
- API contract compatibility for every existing tender route;
- authorization and actor attribution for every mutation.
